# Remote ComfyUI 性能优化计划

## 目标与范围

让手机在局域网中更快打开电脑图库、产物列表和全屏预览，同时控制手机流量、内存及 Windows Gateway 的磁盘占用。本计划针对现有 Expo React Native 手机端、FastAPI Gateway 和 SQLite 索引；生成模型本身的 GPU 耗时单独记录，不与界面加载时间混为一谈。

先采集基线，再以同一台手机、同一 Wi-Fi、同一批测试图片对比。以下是首轮建议验收目标，基线测出后可按设备能力调整：

| 场景 | 建议目标（P95） | 同时观察 |
| --- | --- | --- |
| 打开 50 张图片的图库首屏 | 1.5 秒内看到首批可用缩略图 | 请求次数、传输字节数、图片解码内存 |
| 第二次打开同一图库首屏 | 0.5 秒内显示缓存内容 | 缓存命中率、后台校验耗时 |
| 点击图片进入全屏预览 | 先立即显示缩略图，2 秒内显示原图（普通局域网） | 原图大小、首帧时间、失败率 |
| 打开 100 个产物的列表 | 滚动无明显卡顿 | 帧率、内存峰值、视频请求数 |
| 10,000 张图片的目录翻页 | API P95 小于 300 毫秒（不含首次索引） | SQLite 查询耗时、扫描耗时 |

## 现状与瓶颈

1. `server/app/api/public.py` 中的 `/library-images/{id}/thumbnail` 直接调用原图接口。手机图库虽然使用 `thumbnail_url`，实际仍下载并解码原图。这是预览慢和流量大的首要原因。
2. 同一文件的图库列表接口每次调用都会执行 `_sync_library`：遍历目录并对每张图执行数据库写入。目录变大后，翻页、切换目录都会等待全量扫描。
3. `apps/mobile/App.tsx` 中的产物卡片直接加载图片原件，视频卡片则为每个项目创建播放器。卡片多时会增加网络请求、解码和播放器资源占用。
4. 图库和产物使用 `ScrollView` 与数组直接渲染全部已加载项目；`加载更多` 后仍保留所有组件。产物列表接口目前返回全部记录，没有分页。
5. 手机端仅在保存、分享时将文件下载到临时目录，缺少可复用、有配额和失效规则的预览缓存。重复进入预览可能重复请求。
6. 图片原图接口用 `read_bytes()` 整文件读入内存；产物读取虽然支持 HTTP Range，但仍要观察大视频并发读取时的内存、首帧和磁盘吞吐。
7. 任务页每 5 秒轮询一次，不论页面是否可见或任务是否还在运行。此项不是首要瓶颈，但可以减少空闲请求。

## 分阶段实施

### P0：测量并修复服务器缩略图与索引（最高优先级）

**1. 建立可重复的性能基线。** 准备 50、1,000、10,000 张图片的测试目录，以及不同尺寸的图片和视频产物。记录 Gateway 的接口耗时、响应大小、目录扫描次数；手机记录首屏可见时间、首次预览时间、再次预览时间、滚动卡顿和内存峰值。测试区分冷启动、热启动、首次访问及缓存命中。

**2. 真正生成缩略图。** Gateway 为图库图片生成最长边约 320 px 的 WebP 缩略图，产物图片另生成适合卡片的缩略图；视频产物生成单张封面。缩略图按需生成并原子写入专用缓存目录，避免并发重复处理。保留图片方向，限制解码像素，损坏文件返回占位图或明确错误。缩略图接口只返回小图，原图接口只用于全屏预览、保存和上传引用。

**3. 将目录扫描移出列表请求。** 目录新增或变更时触发后台增量扫描，列表 API 只查 SQLite。扫描按文件大小与修改时间更新索引和缩略图版本，删除索引中已消失的文件；提供手动刷新及最近扫描时间。添加适合 `library_id + mtime + id` 的索引，改用稳定游标分页，避免大量翻页时 `OFFSET` 退化或扫描期间重复、漏项。

**4. 改善文件传输。** 原图使用流式文件响应，避免一次读入内存。继续验证产物视频的 Range 响应和播放器拖动行为。对媒体使用稳定的版本标识、`ETag` 或 `Last-Modified` 与条件请求；删除或替换后必须失效。令牌鉴权仍在每次请求执行，不把令牌写入 URL。

**P0 验收：** 缩略图端点返回真实的小图，50 张图库首屏传输量相对现状明显下降；10,000 张目录的翻页不触发全量磁盘扫描；修改或删除文件后不会长期显示旧图。

### P1：手机预览缓存与按需渲染

**1. 建立磁盘缓存管理器。** 缩略图优先由图片组件的内存/磁盘缓存处理；原图预览按需下载到 App 缓存目录，并以 `服务器地址 + 资源类型 + 资源 ID + 版本` 组成缓存键。缓存前先显示小图，下载完成后切换原图。相同资源并发请求合并，失败可重试，离线时允许显示已缓存的图并标注状态。

**2. 明确缓存配额与清理。** 首版可设缩略图 150 MB、原图 500 MB 的可配置上限，采用 LRU 清理。视频默认只缓存封面，不自动缓存完整视频；用户保存或分享时复用已下载的同版本文件。解除配对、切换服务器、令牌撤销、删除产物时清理相关缓存和预览状态。缓存目录不存明文令牌，并避免将受保护原图暴露给其他 App。

**3. 列表虚拟化。** 图库和产物列表改用 `FlatList` 等按需渲染组件，只加载可见项目及少量预取项目；图库继续分页，产物 API 增加分页。图片组件指定合适的解码尺寸，列表使用缩略图，进入全屏才加载原图。视频列表只显示封面与播放按钮，点击后才创建播放器，离开预览即释放。

**P1 验收：** 第二次进入同一图库首屏能优先显示本地缓存；100 个产物滚动时不会同时创建大量播放器；删除或更换服务器后不会显示错误的旧图；手机缓存用量保持在设定上限内。

### P2：状态更新与细节优化

- 任务轮询只在任务页可见或仍有进行中任务时运行；后台降频，完成后停止。必要时再引入事件推送，并保留断线后的状态补查。
- 图库切换和翻页时取消或忽略过期请求，限制同时下载的图片数量，优先加载屏幕内项目。
- 对大图做渐进式体验：先显示缩略图、加载进度与失败重试；缩放预览保持原始清晰度，避免一直放大低分辨率小图。
- 管理页展示索引图片数、最后扫描时间、缩略图占用及清理入口，便于发现异常增长。

## 实施顺序与估算

| 顺序 | 工作包 | 估算 | 前置条件 |
| --- | --- | --- | --- |
| 1 | 测量埋点与基线 | 0.5–1 天 | 无 |
| 2 | 真实缩略图、视频封面、文件响应 | 2–3 天 | 基线样本 |
| 3 | 后台增量索引与分页 | 2–3 天 | 数据迁移方案 |
| 4 | 手机磁盘缓存与失效 | 2–3 天 | 稳定资源版本 |
| 5 | 虚拟列表、按需视频播放器 | 1–2 天 | 缩略图接口 |
| 6 | 轮询与预取细节、回归验收 | 1–2 天 | 前五项 |

估算仅用于排期，不承诺具体耗时。优先完成服务端缩略图和索引，再评估手机缓存收益；单纯给当前“大图缩略图”加缓存只能改善第二次打开，无法解决首次加载与内存压力。

## 验证与回归重点

- 对同一批媒体重复测冷/热加载的 P50、P95、请求数、总传输量和峰值内存，保留优化前后数据。
- 验证图片修改、删除、目录停用、产物删除、设备解绑和服务器地址切换后的缓存失效。
- 验证手机弱网、断网重连、连续快速翻页、超大图片、损坏图片与多个手机同时浏览。
- 验证缩略图和原图都经过现有设备鉴权与白名单校验；缓存文件不会绕过访问权限。
- 确认视频首帧、拖动播放、保存/分享与图片双指缩放未回退。

本文件是优化计划，尚未实施其中的性能改动；实际效果以基线和完成后的对比测量为准。
